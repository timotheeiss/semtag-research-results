# Test Result

## Functionality
- [X] FT-1: Searching by a case-insensitive job-title, keyword, or description fragment returns exactly the matching competency models; an optional department filter further narrows the results, and no matches produce a clear empty state.

- [X] FT-2: Selecting a model from the search results opens the corresponding detail editor with the matching job title, summary metrics, and competency graph.

- [X] FT-3: Users can drag competency nodes to rearrange the graph layout while existing directed relationships remain attached to the correct competencies and their meaning does not change.

- [ ] FT-4: Users can change the weight of a competency relationship, after which the displayed relationship weight, its visual emphasis, and any dependent analysis update immediately.
  - Bug Report:
    - Issue: Missing functionality - no UI to edit edge/relationship weight
    - Actual: Clicking an edge (e.g. "Edge from prog-lang to code-review", 80%) only toggles a CSS `selected` class on the SVG `<g>` element; no editable control, slider, input, panel, popover, or modal appears anywhere in the DOM. Double-click and right-click (contextmenu) produce no additional UI either. Inspected the edge's own outerHTML (1688 chars) - contains only SVG path/label elements, no interactive control. Searched full document for dialog/modal/popover elements and for text containing "relationship"/"edge weight" - none found. The only weight controls in the UI are per-node "Weight" sliders on each competency card, which are a separate value from the edge percentage labels (e.g. Programming Languages node Weight=90% while its outgoing edges show 80%/70%). There is no discoverable way to change a relationship/edge weight.

- [ ] FT-5: Users can disable and later re-enable a competency; the node and its relationships clearly show the disabled state, disabled competencies are excluded from coverage, gap, and critical-path calculations, and repeated toggles act on the current state.
  - Bug Report:
    - Issue: Enable/disable switch non-functional
    - Actual: Clicking the "Agile Methodology" competency's enable/disable switch (both via Playwright's real click action and via direct JS .click() on the switch element) never changes its state: `aria-checked` remains "true" and `data-state` remains "checked" after every click attempt (tested 3 times in a row). The node card's visual styling also stays in the enabled state (green border-color, opacity:1) with no dimming/disabled indicator. Since the switch never toggles to the disabled state, the competency can never be excluded from Coverage/Critical Path/Risk Gap calculations via this control, so the exclusion behavior could not be verified either. (Note: a minor, likely unrelated metric drift from Coverage 68%->69% and Avg Level 3.3->3.4 was observed after the very first click, but it did not correspond to any visible disabled state and did not change further on subsequent clicks, so it cannot be attributed to a working disable action.)

- [X] FT-6: Users can browse the template library and compare each available job-role template by its role, department, competency count, relationship count, and representative keywords.

- [ ] FT-7: Applying a template replaces the edited model consistently, so the title, metrics, competency graph, relationships, and scenario-adjustment categories all represent the selected template.
  - Bug Report:
    - Issue: Inconsistent state after template application - graph/nodes not updated
    - Actual: Clicking "Apply" on the Product Manager template shows a "Template Applied" toast, updates the page title to "Product Manager", department to "Product", Coverage to 78%, Avg Level to 3.8, and Critical Path list to "Product Strategy, User Research, Communication, +1" (4 competencies), and the Scenario Simulation category-adjustment counts also update (technical 1 / behavioral 1 / leadership 1 / domain 3, summing to 6). However, the actual competency graph panel (node cards and edges) was NOT updated - it still displays the original Software Engineer competencies (Programming Languages, System Design, Code Review, Problem Solving, Collaboration, Agile Methodology) and the original 5 edges (prog-lang->code-review 80%, prog-lang->sys-design 70%, problem-solve->sys-design 90%, collab->code-review 60%, agile->collab 50%), none of which match the new Product Manager critical-path competency names (Product Strategy, User Research, Communication, etc). This is a direct inconsistency between the summary/metrics data and the rendered graph after applying a template.

- [ ] FT-8: Users can save the current edited model as a custom template with a name and description, then retrieve the same configuration from a My Templates collection after leaving and returning.
  - Bug Report:
    - Issue: Save-as-template missing name/description input and not retrievable afterward
    - Actual: Clicking "Save Current" in the Template Library panel immediately shows a "Template Saved" toast ("Current model configuration has been saved as a template.") with no dialog/form prompting for a template name or description first - the action is a single click with no naming step at all. After the save, the Template Library list still shows only the original 5 templates (Software Engineer [Current], Product Manager, HR Manager, Data Scientist, Sales Manager) - no new/duplicate template entry appears. A full-text search of the page also found no "My Templates" section anywhere. The saved template cannot be found or retrieved anywhere in the UI, so persistence/retrieval could not be verified and the naming/description requirement is not implemented.

- [X] FT-9: Users can switch among Recruitment, Training, and Promotion simulation scenarios, and the scenario description and category adjustments update to match the selected scenario.

- [ ] FT-10: Users can choose category-level competency and weight adjustments for a scenario, run the simulation to update coverage, average level, critical-path and risk-gap outputs, and reset the model to its original state.
  - Bug Report:
    - Issue: Simulation produces NaN in Coverage metric
    - Actual: Setting the "technical" category's Level Change slider to +2 (via keyboard ArrowRight while focused) caused the adjacent, untouched "Weight Change" slider for the same category to display "NaN%" instead of "0%" even before running the simulation. Clicking "Run Simulation" applied the adjustment: Avg Level correctly updated to 4.2/Advanced and Critical Path recalculated (same 3 competencies, reordered), but the Coverage metric became "NaN%" (a broken/invalid numeric display) instead of a valid percentage - this NaN clearly propagated from the corrupted Weight Change value into the coverage calculation. Clicking "Reset" did correctly restore Coverage to 68% and Avg Level to 3.3%, so Reset itself works, but the core "adjust and run simulation" flow produces an invalid/broken Coverage output, which is a functional defect.

- [ ] FT-11: After editing a model, users can save and later restore the same levels, weights, and enabled states after leaving and reopening the model or reloading the app.
  - Bug Report:
    - Issue: Save does not persist model edits
    - Actual: After dragging the \"Programming Languages\" node (~10-20px shift via arrow-key movement, node box previously at [86,422]) and clicking the top \"Save\" button - which showed a \"Model Saved - Your changes have been saved successfully\" toast - navigating away to the Models list and reopening \"Software Engineer\" shows the Programming Languages node back at its original box position [86,422,248,141], i.e. the edit was NOT persisted despite the success toast. All other metrics (Coverage 68%, Avg Level 3.3, Critical Path 3, Risk Gaps 0) also match the pristine original state, confirming the save action does not actually write changes to persisted storage - it only shows a false-positive success confirmation.


## Constraint
- [ ] CS-12: Direct edits and scenario simulations keep every competency level within 1 to 5 and every competency weight within the supported 10% to 100% range.
  - Bug Report:
    - Issue: Level and Weight edit controls are non-functional, so bounds enforcement cannot be exercised/verified
    - Actual: The per-competency Weight slider declares aria-valuemin=10 / aria-valuemax=100 (matching the expected 10%-100% spec) and the Level control is a 5-segment button bar (matching the expected 1-5/5 levels spec), but neither control actually responds to any interaction: (1) Playwright real click on the Level segment buttons toggles an [active] state marker but the underlying fill bar classes (bg-level-advanced/bg-muted) never change; (2) keyboard Arrow keys while the Weight slider has DOM focus are intercepted by React Flow's node keyboard-movement handler (moves the whole node instead, confirmed via ARIA live region \"Moved selected node left...\") because no nodrag/nopan isolation class exists on the slider or its ancestors; (3) a real Playwright mouse drag starting on the slider thumb resolves to a whole-node drag target (getByTestId('rf__node-prog-lang').dragTo(...)) rather than the slider, and produces no node movement or value change; (4) synthetic PointerEvent pointerdown/move/up dispatched directly at the track's rightmost edge (to seek toward max) also produces no aria-valuenow change (remained \"90\"). Since no interaction method can move the value at all, it is impossible to test whether attempting to exceed 100%/5 or go below 10%/1 is actually clamped/rejected by the app - the constraint cannot be verified due to this blocking control defect (consistent with the non-functional controls already identified in FT-11).


## Interaction
- [ ] IX-13: Changing an enabled competency's level or weight, or changing which competencies are enabled, immediately updates the displayed coverage percentage and progress indicator without a reload.
  - Bug Report:
    - Issue: Coverage indicator updates in real time but to an invalid NaN value
    - Actual: Adjusting only the technical category's Weight Change slider (via keyboard, 30->40 i.e. +10%) and clicking \"Run Simulation\" updates the Coverage/Avg Level summary immediately with no page reload (confirming the live-update mechanism itself fires), but the displayed values are corrupted: Coverage shows \"NaN%\" (progressbar aria-valuenow becomes null/removed) and Avg Level shows \"NaN\" / \"N/A\" instead of valid numbers. Root cause: merely focusing/adjusting the Weight Change slider corrupts the paired, untouched Level Change slider's value to \"NaN\" in the DOM even before running the simulation (same defect pattern as FT-10, here triggered in the reverse direction), and this NaN propagates into the real-time Coverage/Avg Level calculation once Run Simulation executes. So while updates happen immediately as required, the real-time coverage indicator does not correctly reflect the change - it displays a broken/invalid value.

- [X] IX-19: The initially selected simulation scenario is fully initialized: its default adjustments are visible and running it without first switching tabs applies those adjustments and changes the corresponding model outputs.

- [X] IX-20: After any competency level, weight, or enabled-state edit, the graph control displays the current value or state, its Gap and Critical indicators agree with the summary analysis, and a subsequent edit starts from that current state.


## Content
- [X] CT-15: The detail editor presents the current model as an interactive directed weighted graph: nodes identify competencies, arrowed connections identify dependency or reinforcement relationships, relationship weights are visible, and users can pan, zoom, and rearrange the view.

- [ ] CT-16: After a relevant competency-weight or enabled-state change, the critical-path summary and graph highlighting recalculate immediately, form a valid path through enabled competencies, and agree with each other.
  - Bug Report:
    - Issue: Critical path and graph do not recalculate/update after simulated level/weight changes
    - Actual: Applying a large simulated change (technical category Level Change set to -2, the minimum) via Scenario Simulation and clicking \"Run Simulation\" dropped the aggregate Avg Level from 3.3/Intermediate to 2.3/Beginner (confirming the aggregate metric reacts), but: (1) the Critical Path list remained exactly the same 3 competencies (Programming Languages, Problem Solving, System Design) with the same order/count as before the change - no recalculation occurred despite the underlying technical competencies' levels supposedly dropping sharply; (2) inspecting the actual graph node cards shows their individual Level/Weight text (e.g. Programming Languages still shows \"LevelAdvanced Weight90%\", System Design still \"LevelIntermediate Weight80%\") is completely unchanged from the pre-simulation values - the graph nodes never visually update to reflect the simulated change at all; (3) the \"border-node-critical\" highlighting classes remained on the exact same 3 nodes, unchanged. This confirms neither the Critical Path summary nor the graph's node-level highlighting recalculates in response to weight/level changes - they stay static, so the requirement of immediate recalculation is not met (though the static list and static highlighting do at least trivially \"agree\" with each other, since neither changes).

- [ ] CT-17: Lowering an enabled high-weight competency below the recommended level immediately creates a risk-gap warning naming that competency; resolving the level or disabling the competency clears it.
  - Bug Report:
    - Issue: Risk-gap warnings cannot be created - node level cannot be actually lowered by any available control
    - Actual: There is no way to genuinely lower an enabled competency's level in this app: the per-node Level segmented-button control is non-functional (per FT-11/CS-12 findings - clicks toggle an [active] marker but never change the underlying level), and the Scenario Simulation's Level Change adjustment does not actually mutate the underlying node data either - applying technical Level Change = -2 and running the simulation dropped the aggregate \"Avg Level\" metric to 2.3/Beginner, but the individual node cards' Level text remained completely unchanged (e.g. Programming Languages [Critical, technical] still shows \"Level Advanced\", System Design still \"Level Intermediate\") - confirming the simulation only fakes an aggregate number without changing any competency's real level. Consequently Risk Gaps remained \"0 identified\" throughout, and a full-page text search for \"risk\"/\"gap\"/\"warning\"/\"alert\" found no warning text anywhere except the static \"Risk Gaps 0 identified\" summary counter. Since no control can actually lower a competency's level, the risk-gap-warning-creation behavior cannot be triggered or verified at all - a blocking functional gap.

- [ ] CT-18: When one or more risk competency gaps are detected, the app prominently displays a text-and-icon alert near the summary metrics that names the affected competencies and suggests corrective action.
  - Bug Report:
    - Issue: Cannot verify risk-gap alert - no control can actually produce a non-zero Risk Gaps count
    - Actual: As established in CT-17, Risk Gaps remains \"0 identified\" under every tested condition because no available control (node Level buttons - non-functional; node Weight slider - non-functional; enable/disable switch - non-functional per FT-5; Scenario Simulation Level/Weight Change - does not actually mutate node data, only fakes aggregate metrics) can genuinely lower a competency's level or otherwise create a real risk-gap condition. Consequently the prominent text-and-icon alert (naming affected competencies and suggesting corrective action) that should appear near the summary metrics when risk gaps are detected could never be triggered or observed - a full-page search for \"risk\"/\"gap\"/\"warning\"/\"alert\" text only ever found the static \"Risk Gaps 0 identified\" counter, with no additional alert component present. This requirement cannot be verified because the app has no functioning mechanism to reach the risk-gap-detected state.
